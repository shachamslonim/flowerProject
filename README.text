===============================================================
  Flower Vision Project
===============================================================

## Quick Start: Open the GUI

The full pipeline (species ID -> open/closed state -> care instructions)
has a Streamlit GUI. It needs the API running first, then the GUI itself:

  1) Start the API (from the project root, in one terminal):
       uvicorn api.main:app --host 127.0.0.1 --port 8877

  2) Start the GUI (from the project root, in a second terminal):
       streamlit run gui\app.py --server.headless true

  3) Open the URL Streamlit prints (default: http://localhost:8501)
     in a browser.

See "Combined Pipeline: API (FastAPI + Swagger), GUI (Streamlit),
Monitoring (LangSmith)" below for the full GUI walkthrough, all API
endpoints, and the Swagger UI at http://127.0.0.1:8877/docs.

## Setup

Go to the project:
  cd C:\flowerAI\flowerProject

Create and activate virtual environment (PowerShell):
  py -m venv .venv
  .venv\Scripts\Activate.ps1

Install dependencies:
  python -m pip install --upgrade pip
  pip install -r requirements.txt

## Credential Setup

Google Cloud Vision requires a Service Account key JSON file.
Do NOT use OAuth client_secret JSON files.

1) Enable Vision API in Google Cloud Console:
   https://console.cloud.google.com/apis/api/vision.googleapis.com

2) Create a Service Account:
   IAM & Admin -> Service Accounts -> Create -> Keys -> Add Key -> JSON

3) Save the downloaded JSON file in the project folder.

4) Create a .env file with:
   GOOGLE_APPLICATION_CREDENTIALS=your_service_account_key.json
   IMAGE_PATH=photo/your_flower.jpg

===============================================================
  Running flower_vision.py (Single Image Detection)
===============================================================

Identifies a flower from a single image using Google Vision API.

Usage:
  python flower_vision.py
  python flower_vision.py path\to\flower_image.jpg

The script reads IMAGE_PATH from .env or accepts a command-line argument.

Output:
  - Detected labels with confidence scores
  - Likely flower name(s) from the built-in keyword list

===============================================================
  Running test_flower_accuracy.py (Accuracy Test)
===============================================================

Tests the Google Vision API accuracy for flower identification
across multiple flower types from the photo/ folder.

## How It Works

The test uses a 2-tier detection approach:
  Tier 1: Label Detection (up to 15 labels)
  Tier 2: Web Detection (fallback if Tier 1 doesn't match)

For each flower in test_flowers.json:
  - Sends up to 3 photos through the API
  - Checks if the expected flower name appears in returned labels (case-insensitive)
  - If any photo matches on any tier, the flower is marked as DETECTED
  - If none match, retries with additional photos from the folder

## Configuration (.env)

Required:
  GOOGLE_APPLICATION_CREDENTIALS=your_service_account_key.json

Optional:
  RETRY_NOT_MATCHED=2

  RETRY_NOT_MATCHED controls how many times to retry unmatched flowers
  using additional photos from the same folder. Each retry picks the
  next 3 photos (not previously tested). Set to 0 to disable retries.

## Test Data (test_flowers.json)

JSON array where each entry has:
  - expected_name: the flower name to match (lowercase)
  - image_paths: array of relative paths to test photos
  - folder_name: source folder for display

Example entry:
  {
    "expected_name": "rose",
    "image_paths": [
      "photo/002_Rose/open/open_00002_pexels_38251394.jpg",
      "photo/002_Rose/open/open_00006_pexels_38531905.jpg",
      "photo/002_Rose/open/open_00008_pexels_12912281.jpg"
    ],
    "folder_name": "002_Rose"
  }

## Running the Test

  .venv\Scripts\Activate.ps1
  python test_flower_accuracy.py

## Output Format

Per-flower results:
  [1/15] 002_Rose | Expected: rose
    Photo 1/3 [Tier 1] Labels: Flower (0.99), Rose family (0.84), ...
    Result: DETECTED (via Label Detection - Rose family (0.84))

Retry rounds (if RETRY_NOT_MATCHED > 0):
  RETRY ROUND 1/2 (2 flowers to retry)
    [008_Ageratum] | Expected: ageratum (trying 3 new photos)
    Result: DETECTED (via Web Detection)

Summary:
  SUMMARY
  Total tested:  15
  Matched:       14
    - via Label Detection:  9
    - via Web Detection:    5
  Not matched:   1
    - 009_Statice_Limonium (statice)
  Errors:        0
  Accuracy:      93.3%

## Adding More Flowers to Test

1) Find the flower folder under photo/ (e.g., photo/016_Celosia/open/)
2) Pick 3 photos from the open/ subfolder
3) Add an entry to test_flowers.json:
   {
     "expected_name": "celosia",
     "image_paths": [
       "photo/016_Celosia/open/open_00001_xxx.jpg",
       "photo/016_Celosia/open/open_00002_xxx.jpg",
       "photo/016_Celosia/open/open_00003_xxx.jpg"
     ],
     "folder_name": "016_Celosia"
   }

## Matching Logic

- Case-insensitive "contains" match
- Expected name "rose" matches labels like "Rose", "Rose family", "Garden roses"
- Tier 1 (Label Detection) returns up to 15 labels with confidence scores
- Tier 2 (Web Detection) returns web entity names from reverse image search
- If any photo in the set matches on any tier, the flower is DETECTED

## Notes

- Photos must be from the "open" subfolder (open state flowers)
- The API struggles with less common flowers (e.g., Statice, Ageratum)
- Web Detection often catches flowers that Label Detection misses
- Retries help by testing different photos of the same flower

===============================================================
  Combined Pipeline: API (FastAPI + Swagger), GUI (Streamlit), Monitoring (LangSmith)
===============================================================

The three components (flower_vision, flower_state_ai, InstructionsForTreatment)
are combined into a single pipeline: photo -> species identification ->
open/closed state -> care instructions. The pipeline is exposed through one
FastAPI service (folder api/), driven by a Streamlit GUI (folder gui/), and
traced end-to-end with LangSmith (folder monitor/).

## Install dependencies for the API and GUI

  pip install -r api\requirements.txt
  pip install -r gui\requirements.txt

(also make sure requirements.txt, flower_state_ai\requirements.txt, and
InstructionsForTreatment\requirements.txt are installed, since the API
imports all three components)

## Running the API (with Swagger UI)

Start the server from the project root:

  uvicorn api.main:app --host 127.0.0.1 --port 8877

Once running, open in a browser:

  http://127.0.0.1:8877/          -> redirects to Swagger UI
  http://127.0.0.1:8877/docs      -> Swagger UI (interactive API docs, try endpoints here)
  http://127.0.0.1:8877/redoc     -> ReDoc (read-only API docs)
  http://127.0.0.1:8877/openapi.json -> raw OpenAPI schema

Swagger UI lists every endpoint with its request/response schema and lets
you upload a test image and call the endpoint directly from the browser,
with no need for curl or Postman.

## API Endpoints

  GET  /health
    Simple liveness check, returns {"status": "ok"}.

  POST /identify
    Form fields: image (file, required), vision_backend ("google" or
    "paligemma", default "google").
    Identifies the flower species in the photo.

  POST /state
    Form fields: image (file, required), species_name (required),
    arch ("mobilenet_v2" / "tiny_cnn" / "paligemma_state_only", optional -
    auto-picked per species from flower_state_ai\models\model_recommendations.json
    if omitted).
    Classifies the flower as open or closed.

  POST /instructions
    JSON body: species_name, is_open, yellow_leaves, leaves_falling,
    language ("en"/"he"), mode ("template"/"llm"), audience, llm_model,
    translate, read, speak_engine.
    Generates the care-instructions text (and optional read-aloud audio).
    NOTE: is_open is InstructionsForTreatment's own flag and its meaning is
    inverted - is_open=True renders the CLOSED-flower instructions and
    is_open=False renders the OPEN-flower instructions (see
    InstructionsForTreatment\README for details).

  POST /pipeline
    Form fields: image (file, required), vision_backend, state_arch,
    yellow_leaves, leaves_falling, language, mode, audience, llm_model,
    translate, read, speak_engine (all optional, same meaning as above).
    Runs identify -> state -> instructions as one traced request. This is
    the endpoint that shows up as a single end-to-end trace in LangSmith.

  GET  /audio/{filename}
    Serves a generated read-aloud audio file back to the caller (used by
    the GUI to play audio returned from /instructions or /pipeline).

## Running the GUI (Streamlit)

With the API already running (see above), start the GUI from the project
root in a separate terminal:

  streamlit run gui\app.py --server.headless true

Streamlit prints a local URL (default http://localhost:8501) - open it in
a browser. The GUI is a pure API client: every action calls the FastAPI
endpoints above over HTTP, it never imports flower_vision, flower_state_ai,
or InstructionsForTreatment directly.

GUI walkthrough:
  1) Upload a flower photo.
  2) Choose a vision backend (Google Vision or PaliGemma) and click
     "Identify" - shows the detected species and raw labels.
  3) Edit the species name if needed, choose a state-classification model
     (pre-selected from model_recommendations.json) and click
     "Classify state" - shows open/closed.
  4) Choose language, mode, audience, and read-aloud options, then click
     "Generate instructions" - shows the final care instructions text and,
     if read-aloud was requested, an audio player.
  Alternatively, expand "Run the full pipeline in one click instead" to do
  all three steps in a single request.

If the GUI needs to reach an API running somewhere other than
http://127.0.0.1:8877, set the API_BASE environment variable before
launching Streamlit:

  $env:API_BASE = "http://127.0.0.1:8877"
  streamlit run gui\app.py --server.headless true

## Monitoring with LangSmith

1) Sign up at https://smith.langchain.com and create an API key.
2) Add to the project-root .env file:
     LANGCHAIN_API_KEY=your_langsmith_api_key
     LANGCHAIN_PROJECT=flower-pipeline
3) Start the API as usual - on startup it calls monitor\langsmith_setup.py's
   init_langsmith(), which enables tracing automatically when the key is
   present (and no-ops with a warning if it's missing, so tracing is
   optional and never blocks the pipeline from running).
4) Call /pipeline (via Swagger, the GUI, or curl) and check
   https://smith.langchain.com for a trace named after the run_pipeline
   function, showing identify -> state -> instructions as nested spans
   (LLM-mode instruction generation shows further nested token/latency
   detail from the underlying Ollama call).
